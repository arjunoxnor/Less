# Backend security review, 2026-08-13

Run against `functions/api/[[path]].ts` (the Cloudflare Pages Function over D1
and KV) and the `duet/` Worker with its `DuetRoom` Durable Object. This is the
review that was queued when the Codex subscription ended and never ran.

Threat model, stated honestly so nothing below is mis-read: LESS is a free app,
anyone can open a document without an account, and duet rooms are deliberately
shareable by link. "Anyone with the link can edit" is the INTENDED design. What
counts as a finding is someone WITHOUT the link getting in, one user reaching
another's account data, or the service being trivially abusable.

Status of each item is tracked at the bottom of this file.

# Part 2: Backend security review

## A. `functions/api/[[path]].ts` (frozen, report only)

**1. Anyone can mint an identity and write to D1 with no credential, and no data endpoint is rate limited. Severity: high.**
`userFrom` (`:237-241`) accepts `Authorization: Bearer code:<any string of 16+ characters>` and derives the user id from its SHA-256. There is no registration, no rate limit on anything except `auth/google` (`:259`) and `auth/claim` (`:279`), and no cap on rows or bytes per identity. `MAX_BODY_BYTES` (`:54`) is the only bound at 3 MB per request. `POST /api/scripts/<id>/versions` (`:444`) additionally never checks that `<id>` belongs to the caller and has no cap on version count, while `GET` only ever returns 100, so nothing prunes them.

What an attacker gets: unauthenticated, unlimited, 3 MB-per-request durable storage in `less-db`, with a fresh identity per request so nothing is even attributable. Once D1 hits its storage ceiling every real user's sync starts failing. This is structural to the sync-code design rather than a coding slip, which is why it needs a deliberate answer (a per-IP limiter on all mutating paths, plus a per-identity row and byte quota) rather than a patch.

**2. A leaked sync code is a silent, irreversible transfer of the victim's whole library. Severity: high, but requires the code.**
`POST /api/auth/claim` (`:276`) runs `UPDATE scripts SET user_id=? WHERE user_id=?` (`:291-308`). It **moves** the rows, so the source account is emptied. Whoever holds the code both reads everything and destroys the owner's cloud copy, with no notification and no undo. The code itself is strong (20 characters from a 31-symbol alphabet, about 99 bits, `lib/cloud/auth.ts:44-50`), so this is not brute-forceable; the point is that the blast radius of a shoulder-surfed or screenshotted code is total.

**3. The KV rate limiter is bypassable by concurrency and collapses under load. Severity: medium.**
`rateLimited` (`:92-110`) is a non-atomic read-modify-write: `parseInt(await RATE.get(k)) + 1` then `put`. N simultaneous requests all read the same value and all write 1. Cloudflare KV also caps writes at roughly one per second per key, so sustained hammering makes `put` throw, the `catch` at `:107` falls back to `memLimited`, and `memLimited` is a per-isolate `Map` that Cloudflare will spread across many isolates. The effective limit on `auth/claim` is far above the intended 10/min. `cf-connecting-ip` itself cannot be spoofed, which is correct.

**4. No guard that `SESSION_SECRET` is bound. Severity: latent, but catastrophic if it fires.**
`hmacKey(env.SESSION_SECRET)` (`:136`). If the secret is missing or empty in any environment, the HMAC key is empty and `verifySession` will accept a token anyone can sign, letting an attacker forge `{sub: "<victim google sub>"}`. Google sign-in is currently gated behind `NEXT_PUBLIC_GOOGLE_CLIENT_ID` so the exposure is dormant, but a preview or branch deploy without the secret bound is a full account-takeover primitive. One line (`if (!env.SESSION_SECRET) return fail("misconfigured", 500)`) closes it whenever the file is next unfrozen.

**5. Minor:** `POST /api/scripts/<id>/versions` binds `JSON.stringify(b.content)` unguarded (`:456`); a body with no `content` binds `undefined`, which D1 rejects, producing a 500 rather than a 400. Sessions are 30 days with no server-side revocation (sign-out only clears the client copy), and the token lives in `localStorage` (`lib/cloud/client.ts:11`), so any XSS is a 30-day account compromise.

**What is genuinely sound here, so it does not get re-flagged:** every D1 statement is parameterised, including the dynamic PATCH at `:522` whose `sets` come from a fixed column whitelist. Every SELECT, UPDATE and DELETE binds `user_id`. `PRIMARY KEY (user_id, id)` in `0001_init.sql` means an attacker-chosen `id` on `POST /api/scripts` can only ever collide with their own row. There are no CORS headers and no cookie auth, so there is no cross-origin read and no CSRF. The Google ID token check verifies signature, `iss`, `aud` and `exp`, and the session verifier pins HS256. There is no path on which user A can read or write user B's rows.

## B. `duet/` (changeable)

**1. The Worker is an open, unauthenticated, unrate-limited durable store and relay. Severity: high.**
`authorizeRoom` (`duet/src/security.ts:43-46`) returns `issue-owner` for **any** 43-char base64url `?owner=` value when the room has no stored owner, and `env.ROOMS.getByName(route.token)` (`duet/src/index.ts:88`) materialises a Durable Object for **any** 43-char token. So a plain `wss://…/room/<43 random chars>?owner=<43 random chars>&client=1&session=<22 chars>` creates a room the caller owns and can seed (`protocol.ts:159`).

The bypass that makes this unbounded: the connection rate limiter lives inside the room's own storage (`RATE_STATE_KEY`, `index.ts:201`) and is only consulted **after** `storage.put(OWNER_KEY)` at `index.ts:190`. It therefore only limits repeat connections to the same room. A script creating a new room per request is not limited at all.

What an attacker gets: free durable storage and a free binary relay billed to the Cloudflare account, with no LESS account, no link, and no attribution. Fix that preserves "anyone with the link can edit": derive the token from the owner key (`token === base64url(sha256(ownerKey))`) so only whoever generated the pair can create a room, and add a global per-IP limiter in the Worker `fetch` before `getByName`.

**2. No message-rate or document-size limit once connected. Severity: high.**
Nothing bounds how often a participant sends. Each document-changing frame is up to 4 MB (`protocol.ts:11`), is decoded twice (`validateUpdate` builds a throwaway `Y.Doc` at `protocol.ts:47`, then `applyUpdate` again), and forces a full `storage.put` of the entire re-encoded snapshot (`protocol.ts:253`) before anything is relayed. One participant with the link can pin the Durable Object's CPU and generate unbounded billable storage writes. Fix: a per-socket token bucket in `webSocketMessage`, plus a cap on `encodeSnapshot(doc).byteLength`.

**3. A room becomes permanently unusable once the snapshot outgrows a DO storage value, and normal use reaches it. Severity: medium-high, and it is data loss.**
Nothing caps the document. `MAX_MESSAGE_BYTES` (4 MB) is above the SQLite-backed DO per-value limit, and Yjs snapshots grow monotonically with edit history including tombstones. When `persist` throws, `index.ts:283-297` resets the in-memory doc and closes every socket with 1011; the next connection reloads the last-good snapshot and hits the same wall on the next edit. Everything written after the last successful persist is lost, permanently, and a malicious participant can trigger it deliberately with one message. Fix: cap the document, and compact periodically (re-encode a fresh doc) or shard the snapshot across keys.

**4. Revoke never deletes the document, and abandoned rooms live forever. Severity: medium, privacy.**
`index.ts:151-168` writes `REVOKED_KEY` and returns the final snapshot, but `SNAPSHOT_KEY` stays in Durable Object storage indefinitely. There is no alarm and no TTL anywhere, so every room ever created persists. The user is told "Sharing stopped" and reasonably believes the copy is gone; the full text of their screenplay is still on the Worker. Fix: `deleteAll()` on revoke, plus an alarm that deletes an idle room after N days.

**5. `MESSAGE_QUERY_AWARENESS` is relayed to every peer. Severity: medium.**
`protocol.ts:154-157` and `index.ts:309`. One frame from any participant makes every other peer reply with an awareness update, each of which is relayed to everyone else. With `MAX_ROOM_CONNECTIONS` at 128 that is roughly 16,000 messages per frame sent. Combined with (2), one client can sustain it. Fix: rate-limit query-awareness per socket, or answer it from the room's own awareness table instead of fanning it out.

**6. Ownership can be stolen before the owner first connects. Severity: low, narrow window.**
`createProjectShare` (`lib/collab/duet.ts:216`) mints the token and owner key locally; the room does not exist server-side until someone connects. If the owner copies the link and shares it before ever connecting (offline, Worker down, tab closed), the first recipient to craft `?owner=<their own 43 chars>` becomes the permanent owner. `authorizeRoom` then returns `forbidden` for the real owner's key (`security.ts:50`), locking them out of their own room with no way to revoke it. The fix in (1) closes this too.

**7. The owner credential travels in the query string. Severity: low.**
`params: { owner: ownerKey }` at `lib/collab/duet.ts:369-371`, so it lands in whatever request logging Cloudflare or an intermediary retains. Prefer a header or a post-upgrade challenge. The `x-duet-owner` comparison at `index.ts:154` is also a non-constant-time compare; not practically exploitable across the network, but trivially fixable.

**Explicitly not vulnerabilities, so they are not re-flagged:** the 43-char tokens are 256 bits from `crypto.getRandomValues` (`lib/collab/duet.ts:198-200`), so rooms cannot be enumerated. A guest with no `?owner=` cannot seed and is refused outright while the room is empty (`index.ts:193`, HTTP 425). A peer's awareness client id is pinned to its socket (`protocol.ts:141-146`), so cursors cannot be spoofed and a peer cannot impersonate another participant. Probing a nonexistent token returns 404 before any storage write, so it leaves no durable footprint. There is no origin check on the websocket upgrade, but since possession of the link is the intended credential, that is consistent with the threat model rather than a hole.
