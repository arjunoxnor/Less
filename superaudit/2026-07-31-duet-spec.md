# Duet: send a link, write together

Arjun's words: "send your friend a link and then both of you can type on the
same script google docs style and it updates in real time."

This is the largest feature in the app and it touches the save path, which is
the one thing that must never lose work. Read this whole document before
writing code. House style: no em dashes, no emojis, no exclamation marks, in
code, copy or comments. Comments say why, not what.

## Decisions already made, do not revisit

- **Anyone with the link can edit.** No sign-in, no account, no friction. The
  link carries a long random token. The owner can revoke by rotating it.
- **Server-backed, on Cloudflare's free plan.** Durable Objects with the
  SQLite backend are free (100,000 requests and 13,000 GB-seconds a day, 5GB
  storage), which is far beyond two people writing. Peer-to-peer was
  considered and rejected: WebRTC still needs a signaling server, and a guest
  who opens the link later would find nothing.
- **Yjs is the engine.** The editor was deliberately architected to accept it.
  The dependencies are already installed: `yjs`, `y-prosemirror`,
  `y-protocols`, `lib0`, `y-websocket`, `@tiptap/extension-collaboration`,
  `@tiptap/extension-collaboration-caret`.

## Frozen contracts

- `functions/api/**` and `migrations/**` DO NOT CHANGE. Duet is a separate
  Worker, so it needs neither.
- No existing localStorage key changes shape. New keys are additive.
- No new ProseMirror node types. The schema stays one `screenplayLine` node.

## Architecture

### The server: a separate Worker, not the Pages app

Create `duet/` at the repo root, deployed independently as a Worker named
`less-duet`. Do not touch the root `wrangler.toml` or the Pages Function.

`duet/wrangler.jsonc`:

```jsonc
{
  "name": "less-duet",
  "main": "src/index.ts",
  "compatibility_date": "2025-01-01",
  "durable_objects": {
    "bindings": [{ "name": "ROOMS", "class_name": "DuetRoom" }]
  },
  "migrations": [{ "tag": "v1", "new_sqlite_classes": ["DuetRoom"] }]
}
```

`new_sqlite_classes` matters: the SQLite backend is the one that is free.

The Worker routes `GET /room/<token>` with an `Upgrade: websocket` header to
the Durable Object instance named by that token:

```ts
const stub = env.ROOMS.getByName(token);
return stub.fetch(request);
```

### The room: hibernating WebSocket server speaking the y-websocket protocol

`DuetRoom extends DurableObject`. Accept connections with
`this.ctx.acceptWebSocket(server)` (the Hibernation API), NOT `server.accept()`.
Hibernation is what keeps an idle room from burning duration against the free
allowance. Handle `webSocketMessage(ws, message)` and
`webSocketClose(ws, code, reason, wasClean)`.

Speak the standard **y-websocket** protocol so the browser can use the stock
`WebsocketProvider` from `y-websocket` with no custom client:

- Message type 0 is sync (`y-protocols/sync`): `readSyncMessage`, replying with
  sync step 2 and relaying updates to every other client in the room.
- Message type 1 is awareness (`y-protocols/awareness`): relay to every other
  client. Awareness is presence only and is never persisted.
- Encode and decode with `lib0/encoding` and `lib0/decoding`.

Because a hibernating object can be evicted between messages, **the room must
not rely on an in-memory Y.Doc surviving**. On every applied update, persist.
Keep it simple and correct:

- Store the document as a single binary snapshot in DO storage under one key,
  written with `Y.encodeStateAsUpdate(doc)`.
- On wake, load the snapshot and rebuild the Y.Doc before answering anything.
- Debounce snapshot writes (roughly every 2 seconds of activity) and always
  write on the last client disconnecting, so a crash loses at most a couple of
  seconds and a clean exit loses nothing.

A room whose token nobody knows is unreachable, so no auth beyond the token.
Rate-limit connections per IP inside the Worker to keep a leaked token from
being used to hammer the object.

### The client

`lib/collab/duet.ts` owns everything and is the only place that knows about
Yjs. It must expose a small surface: given a project id and a share token,
return a `Y.Doc` and a connected `WebsocketProvider`, plus a `destroy()`.

Wiring it into the editor is where the danger is. Read this twice:

- When a document is collaborative, the TipTap editor must **not** be given
  `content`. The content arrives through Yjs. Passing both is the single most
  common way to end up with the entire script duplicated.
- The Y.Doc is seeded from the local document **exactly once, by the owner,
  and only when the room is genuinely empty**. Guard it: after the provider
  syncs, if the shared XmlFragment is empty and this client is the owner,
  apply the local ProseMirror doc through `prosemirrorToYXmlFragment` (or by
  applying it as an update). If the room already has content, take the room's
  content and never push the local copy over it.
- `Collaboration` replaces the History extension. Remove `History` from the
  extension list when collaborative, or undo will behave incorrectly. The
  existing `lib/editor/undoIntegrity.test.ts` suite covers the non-collaborative
  editor and must keep passing unchanged.
- The existing LWW cloud sync (`lib/storage/useCloudSync.ts`) MUST NOT run for
  a document while it is shared. Two sync systems writing the same document is
  how content gets clobbered. Disable it for collaborative documents and say
  so in the status bar.
- localStorage autosave still runs, as a local mirror for safety, driven by
  the Yjs document rather than competing with it. Losing work is unacceptable
  and that rule does not relax because a second person is typing.

### Presence

Use `@tiptap/extension-collaboration-caret` with the provider's awareness.
Each participant gets a name and a colour. The owner is whatever their account
name is, or "You"; a guest is "Guest" plus a short random suffix until they
type a name. Show who is in the document in the editor's top bar. Awareness is
ephemeral: never write it to storage.

## The product surface

1. **Share.** A "Share" item in the editor's overflow menu opens a modal:
   a single read-only field with the link, a Copy button, plain text saying
   "Anyone with this link can edit this script", and a "Stop sharing" action
   that rotates the token so the old link dies.
2. **The link.** `https://less.oxnorhub.com/#/duet/<token>`. Opening it
   connects to the room and opens the editor on the shared document. No
   sign-in, no account. The route belongs in `components/AppShell.tsx`
   alongside `#/p/<id>`.
3. **The guest's view.** Full editor, same as the owner. The title bar shows
   the script's name and who else is here. A guest's changes are not written
   to any account, only to the room, until stage 3.
4. **Status.** The existing sync indicator shows the collaborative state
   instead of the cloud one: connected, reconnecting, or offline. When the
   connection drops, typing must keep working locally and merge on
   reconnection. That is the whole point of a CRDT: say so in a comment rather
   than adding a warning banner.

## Staging

Build stage 1 and stage 2 in this job. Do not start stage 3.

- **Stage 1:** the Worker, the room, the share link, live co-editing,
  persistence across everyone leaving, reconnection.
- **Stage 2:** presence. Names, colours, carets, who is here.
- **Stage 3 (later, not now):** a guest saving the script into their own
  library, and the owner seeing a list of who has it.

## Testing

Real-time sync cannot be fully proven by unit tests, so test what is testable
and be honest about the rest:

- The room's protocol handling: two simulated clients, one applies an update,
  the other receives it; a late joiner receives the full state; a snapshot
  round-trips through storage. The Worker code should be structured so the
  message handling is a pure-ish function that tests can drive without a live
  DO.
- `lib/collab/duet.ts` seeding logic: seeds an empty room from the local doc,
  does NOT seed a room that already has content, and never seeds twice.
- Token generation: long, random, URL-safe, and unguessable.
- The existing suite must still pass in full, especially undo integrity and
  the storage tests.

Say plainly in your final message which parts are covered by tests and which
need a human with two browser windows, because I will do that pass myself.
