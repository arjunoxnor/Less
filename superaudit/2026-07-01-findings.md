### F1. Body autosave clobbers a newer remote rename: content PATCH always writes the local title unconditionally

- Severity: substantial | Verdict: confirmed -> substantial | Confidence: high
- Evidence: useCloudSync.pushNow always sends the local title with every content save: `const ts = await saveScript(o.projectId, doc, (o.getTitle?.() || "").trim() || o.deriveTitle(doc), tp);` (lib/storage/useCloudSync.ts:127), and the reconcile-time push does the same (line 196-201). The API PATCH writes the title column unconditionally whenever `title` is present: `if ("title" in b) (sets.push("title=?"), vals.push(b.title));` (functions/api/[[path]].ts:384). saveScript always includes title in the body (lib/cloud/scripts.ts:120: `const body = { content, title }`). The per-field guard only protects the CLOCK, not the VALUE: `title_at = CASE WHEN title IS ? THEN title_at ELSE ? END` (line 407) : when the incoming stale title differs from the stored newer title, the CASE takes the ELSE branch and bumps title_at to now, AND the title column is already overwritten. The dashboard reconcile in useProjects runs only once per identity change (useProjects.ts:588-601, `if (now && now !== had) void reconcile`); it does not re-run while a project stays open, so device A never learns of device B's rename before its autosave overwrites it.
- Why it matters: A writer renames a script on their laptop; their desktop still has it open and is idly autosaving (or they type one character). The desktop's content save silently overwrites the new title with the old one AND stamps title_at=now, so on the next sync the laptop's rename is gone for good with no conflict shown. The whole point of the dedicated title_at clock (migration 0004) is defeated for the common case of an open editor, because the content path writes the title value out-of-band.
- Fix plan: Stop sending the title on the content autosave path entirely. In lib/cloud/scripts.ts saveScript, drop `title` from the PATCH body (content-only), and have renames flow exclusively through setScriptTitle (which already exists and is title-only). Callers in useCloudSync.pushNow (line 127), the reconcile push (line 196), and flushBeacon (line 359/367) should pass content (+ optional title_page) only. Title changes already have their own dashboard path (useProjects.rename -> setScriptTitle) and their own dirty flag/clock, so the content save does not need to carry the title. If a derived title for auto-named plain docs must still reach the cloud, route it through setScriptTitle guarded by a value-changed check on the client, or add a server-side guard `title=CASE WHEN ? IS NOT NULL AND title_at < ? THEN ? ELSE title END`. Verify the auto-namer for plain docs still propagates by exercising a plain-doc first-line edit across two sessions.
- Verifier: Traced end to end and it holds. saveScript always puts title in the body (lib/cloud/scripts.ts:120), pushNow always calls it with the derived/explicit title on every content save (lib/storage/useCloudSync.ts:127), and the content-close path does the same (flushBeacon lib/storage/useCloudSync.ts:359,367). The PATCH handler overwrites the title column unconditionally whenever "title" in b (functions/api/[[path]].ts:384). The per-field guard protects only the CLOCK: `title_at = CASE WHEN title IS ? THEN title_at ELSE ? END` (functions/api/[[path]].ts:407) : SQLite evaluates the `title` reference against the ORIGINAL row (as the code comment at lines 404-405 states and as SQLite UPDATE semantics guarantee, independent of SET ordering), so a stale autosave whose title differs from the stored fresh rename takes the ELSE branch and bumps title_at to now while the title column is already overwritten. There is no periodic re-pull (reconcile fires only on identity transition / online / manual syncNow : useProjects.ts:588-601; grep for setInterval/poll found none), so the open editor never learns of the other device's rename before overwriting it. The device that did the rename then adopts the resurrected stale title on its next reconcile via the cloudTitleNewer branch (useProjects.ts:499-505), with titleDirty already cleared to false by its successful setScriptTitle (useProjects.ts:182), so no conflict is shown and the rename is lost. Severity substantial is correct.

### F2. No cross-tab coordination: two tabs on the same device silently diverge and last-writer clobbers

- Severity: substantial | Verdict: confirmed -> substantial | Confidence: high
- Evidence: There is no `storage` event listener anywhere in the codebase (grep for `addEventListener("storage"` / `onstorage` returns no matches). Each editor host mounts its own useCloudSync with a per-instance reconcile guard keyed only to identity+project: `const key = `${user.id}:${projectId}`; if (reconciledFor.current === key) return;` (lib/storage/useCloudSync.ts:171-173). localStorage is shared across tabs but each tab holds an independent TipTap editor in memory. Both tabs subscribe to their own editor 'update' and push (line 249-261). The project index and per-doc keys in localStorage are read/written with no versioning or locking (projects.ts writeIndex line 100-102, saveProjectDoc line 167).
- Why it matters: A writer opens the same script in two tabs (or the dashboard in one tab and the editor in another : a very common browser habit). Tab A writes the doc to localStorage and the cloud; Tab B, holding an older in-memory copy, later autosaves and overwrites both the localStorage doc and the cloud row with its stale content. Because there is no storage-event refresh, neither tab ever notices, and real writing is lost on the same machine : the exact failure the local-first promise is supposed to make impossible.
- Fix plan: Add a `window.addEventListener('storage', ...)` listener at the storage layer (lib/storage/localStore.ts or a new hook) that fires when another tab writes a project doc/index key. In useCloudSync, on a storage event for this projectId's docKey, if the local editor is not dirty, pull the newer localStorage content into the editor via the existing pullInto path; if it is dirty, surface a conflict indicator rather than blindly pushing. At minimum, gate cloud pushes behind a last-write-wins check that re-reads localStorage's lastSavedAt before pushing, and broadcast a BroadcastChannel message on each save so sibling tabs invalidate. Order: implement the storage/BroadcastChannel listener first, then wire the non-dirty auto-pull, then the dirty-conflict UI.
- Verifier: Verified. Grep for addEventListener("storage"/onstorage/BroadcastChannel across the whole repo returns zero matches. Each editor host mounts its own useCloudSync with a per-instance reconcile guard keyed only to identity+project (`const key = ${user.id}:${projectId}; if (reconciledFor.current === key) return;` lib/storage/useCloudSync.ts:171-173) and its own in-memory TipTap editor; each subscribes to its own 'update' and pushes (lib/storage/useCloudSync.ts:249-256). localStorage index/doc writes have no versioning or locking (projects.ts writeIndex:100-102, saveProjectDoc:167). A tab holding an older in-memory doc that then receives a keystroke will push that stale doc, overwriting both localStorage (saveProjectDoc) and the cloud row with no storage-event refresh to reconcile. Real same-machine writing loss on the exact failure the local-first promise is meant to prevent.

### F3. Reconcile pull of a cloud-newer doc into an open editor can silently discard in-progress edits typed after sign-in reconcile completed

- Severity: substantial | Verdict: refuted -> qol | Confidence: medium
- Evidence: useCloudSync reconcile runs exactly once per (user,project) and captures dirtiness only at that instant. If at open the local copy is clean and cloud is newer, it pulls (line 211-215). But the dashboard-level reconcile (useProjects.ts:326) and the per-doc reconcile both fire only on the identity transition. There is NO periodic re-pull. Conversely, the danger case: `reconciledFor.current = key` is set BEFORE the async body runs (line 173), and on any thrown error it is reset to null (line 242) to allow retry : but a successful pull that happens to race a just-started keystroke relies solely on the `typedDuringFetch` snapshot comparison (line 187-189) taken once. Any edit landing in the microtask gap between that comparison and `editor.commands.setContent(content, { emitUpdate:false })` in pullInto (useCloudSync.ts:100) is overwritten with no update event and no dirty flag, because setContent replaces the doc wholesale.
- Why it matters: On a slow connection the fetchScript can take seconds. A writer who opens a project and immediately starts typing can have the first sentence they write replaced by the cloud copy if their keystroke lands in the narrow window after the typedDuringFetch check but before setContent. Because emitUpdate is false, nothing marks it dirty and the lost text is never re-pushed. Rare, but it is a silent-writing-loss path, which the product bar treats as unacceptable.
- Fix plan: In useCloudSync reconcile, re-read `editor.getJSON()` immediately before calling pullInto and re-run the typedDuringFetch comparison against that fresh read; if it changed since the pre-fetch snapshot, take the dirty/push branch instead of pulling. Better: make pullInto refuse to replace content when `optsRef.current.isDirty()` is true at call time, falling back to a conflict path. Also consider snapshotting the pre-pull doc to the version history (snapshotLive) before any cloud-newer pull so it is always recoverable, mirroring what restoreVersion/importContent already do.
- Verifier: The specific race the finding describes does not exist. It claims an edit can land 'in the microtask gap between that comparison (typedDuringFetch, useCloudSync.ts:188-189) and setContent in pullInto (line 100)'. But there is exactly ONE await in the entire reconcile block after the pre-fetch snapshot: `await fetchScript(projectId)` at line 180 (confirmed by grepping every await in the file : lines 127,180,196,220). Everything from the `live = editor.getJSON()` re-read (line 187), through the typedDuringFetch comparison (188-189), the isDirty check (190), and pullInto -> setContent (212 -> 100) executes as one uninterrupted synchronous block with no await. JavaScript's single-threaded event loop cannot dispatch a keydown/update handler between two synchronous statements, so no keystroke can land in the claimed gap. A keystroke during the real async window (the fetch await) is caught by the re-read at line 187 and routed to the push branch, not the pull; a keystroke after the block runs on top of the pulled content and fires its own 'update' (marking dirty and re-pushing). There is no silent-loss path here.
- Corrected evidence: The only await after the pre-fetch snapshot is `await fetchScript(projectId)` (lib/storage/useCloudSync.ts:180). Lines 187-212 (re-read, typedDuringFetch, pullInto->setContent at line 100) are fully synchronous, so the described microtask gap between the comparison and setContent cannot exist.

### F4. Sign-out wipes cloud-derived local docs without flushing pending edits, and drops them if the final push never landed

- Severity: substantial | Verdict: confirmed -> substantial | Confidence: high
- Evidence: signOut (lib/cloud/auth.ts:160-167) synchronously clears the code and session, then the useProjects effect immediately runs `dropCloudProjects(); clearLocalFolders(); clearAllBookkeeping();` on the identity transition (useProjects.ts:594-598). dropCloudProjects deletes every cloudCreated project's doc/title-page/lastSaved keys from localStorage (projects.ts:447-465). Sign-out is triggered from inside the open editor (`onSignOutClick={() => void signOut()}`, ScreenplayBody.tsx:759 / PlainBody.tsx:233). The debounced push (PUSH_DEBOUNCE_MS=1500) may hold unsaved edits; on sign-out userRef becomes null so `pushNow` early-returns (useCloudSync.ts:115) and the token is gone so `api()` returns null (client.ts:87-88). There is no `flush()`/await before the wipe.
- Why it matters: A writer types the last line of a scene and clicks sign out within 1.5s. The debounced cloud push is cancelled (no token/user), and dropCloudProjects then erases the local doc for that cloud project. The last edits existed only in the debounce timer and the editor's memory, both discarded : the work is gone on that device and was never pushed. On a shared/public machine this is the intended wipe, but it should not sacrifice unsynced writing.
- Fix plan: Before tearing down on sign-out, force a synchronous flush: in the sign-out click handlers call the editor host's flush()/flushBeacon() (already exposed by useCloudSync) and await a final pushNow while the token still exists, THEN call signOut(). Alternatively, in signOut() itself, dispatch a 'flush-before-signout' event that the mounted editor awaits, or delay dropCloudProjects until a `beforeSignOut` promise resolves. Ordering constraint: the flush must happen while getToken() still returns the session, so move the clearSession() call to after the awaited flush. Confirm by signing out mid-type and checking the cloud row reflects the last keystroke.
- Verifier: Traced and it holds. signOut (lib/cloud/auth.ts:160-167) synchronously removes the sync code and calls clearSession, which clears TOKEN_KEY/USER_KEY and notifies auth listeners (lib/cloud/client.ts:58-66). That flips user to null, so the useProjects identity effect runs dropCloudProjects()/clearLocalFolders()/clearAllBookkeeping() (useProjects.ts:594-598), and dropCloudProjects deletes every cloudCreated project's doc/title-page/lastSaved keys (projects.ts:447-465). The debounced push (PUSH_DEBOUNCE_MS=1500) holding the last edits does not land: by the time any flush runs, userRef.current is null so pushNow early-returns (useCloudSync.ts:116) and flush itself is gated on userRef.current (useCloudSync.ts:342), and the token is already gone so api() returns null (client.ts:87-88). There is no synchronous flush()/awaited pushNow before the wipe in the sign-out click handlers (ScreenplayBody.tsx:759, PlainBody.tsx:233). The last unsynced keystrokes therefore reach neither the cloud nor a recoverable local index entry. Severity substantial stands.

### F5. localStorage quota exhaustion is swallowed for cloud bookkeeping and folder writes, so a full-storage device can silently corrupt sync state

- Severity: substantial | Verdict: confirmed -> substantial | Confidence: medium
- Evidence: The low-level `set()` returns false on quota failure but nearly all sync-state callers ignore it. writeIndex (projects.ts:100-102) discards the boolean: `lsSet(INDEX_KEY, JSON.stringify(list))` : if the index write fails, cloudCreated/placedAt/titleAt patches, markCloudCreated (line 333), setTitleDirty/setStatusDirty (line 386-404), and tombstone writes (markDeletedTombstone line 418-421) all silently no-op. folders writeAll (folders.ts:85-87) and markFolderTombstone (line 239-243) likewise ignore failure. Only the document body write is checked (saveProjectDoc line 167-168, createProject line 262). deleteProject clears many keys but if a tombstone write fails, a cloud delete is never queued.
- Why it matters: A writer with a full localStorage (large scripts, many projects) can have `markCloudCreated` silently fail: the project stays cloudCreated=false, so on next reconcile it is pushed again as a NEW anonymous create : but the id already exists in the cloud, so ON CONFLICT overwrites content (path.ts:295-297) and, worse, a delete tombstone that failed to write means a deleted project silently resurrects on other devices. Failures compound invisibly precisely when the user has the most work at stake.
- Fix plan: Propagate the boolean from lsSet/writeIndex through the bookkeeping setters (markCloudCreated, setTitleDirty, setStatusDirty, markDeletedTombstone, writeAll, markFolderTombstone) and have useProjects surface a single persistent 'This device is out of storage; sync is paused' banner when any index/tombstone write fails, rather than continuing to operate on an index that did not persist. At minimum, log and set a global degraded flag. Priority order: guard writeIndex and the tombstone writers first (those cause resurrection/duplication), then the dirty flags.
- Verifier: The mechanism is confirmed: lsSet returns false on quota failure (localStore.ts:165-177) but writeIndex (projects.ts:100-102), markCloudCreated (via patchMeta -> writeIndex, projects.ts:333-335), setTitleDirty/setStatusDirty/setTitlePageDirty (projects.ts:386-404), markDeletedTombstone (projects.ts:418-421), folders writeAll (folders.ts:85-87) and markFolderTombstone (folders.ts:239-243) all discard the boolean; only saveProjectDoc (projects.ts:167-172) and createProject (projects.ts:258-264) check it, and there is no degraded-state banner. A silently-failed markCloudCreated leaves cloudCreated=false, so reconcile re-createScripts the same id and ON CONFLICT DO UPDATE overwrites content (path.ts:295-297) : benign if content matches but a clobber if another device's copy is newer. The resurrection consequence is real but partially self-mitigated: in remove() localDelete runs before markDeletedTombstone (useProjects.ts:143 then 149/158) and frees the doc/tp/lock/breakdown keys first, so space is usually available for the tombstone write, and when online deleteScript is attempted immediately regardless of the tombstone. Net: the silent-divergence gap (index/dirty/cloudCreated writes failing with no signal) is a genuine sync-integrity defect worth substantial, though the specific resurrection path is narrower than the write-up implies.
- Corrected evidence: Confirmed swallowed-boolean sites: projects.ts writeIndex:100-102, markCloudCreated:333-335, setTitlePageDirty:386-387, setStatusDirty:394-395, setTitleDirty:403-404, markDeletedTombstone:418-421; folders.ts writeAll:85-87, markFolderTombstone:239-243. lsSet source: localStore.ts:165-177. Mitigation for resurrection: useProjects.ts remove() calls localDelete (line 143) before markDeletedTombstone (149/158), freeing space first, and attempts deleteScript immediately when online.

### F6. Reconcile placement/title/status loops iterate over a stale cloud snapshot but push using freshly-read local meta, so concurrent local edits during a slow reconcile can be lost or reverted

- Severity: qol | Verdict: unverified-qol | Confidence: medium
- Evidence: reconcile fetches `const cloud = await listScripts();` once (useProjects.ts:434) and then runs three sequential await-heavy loops (title/status at 464-530, placement at 535-562, tombstones at 563-574). Each loop re-reads `getProjectMeta(c.id)` fresh (e.g. line 465, 536) but compares against the single old `cloud` snapshot `c`. Every `await` (createScript, setScriptTitle, setScriptStatus, setScriptFolder, deleteScript) yields the event loop; a user rename/status/placement change made in that window updates local meta and its dirty flag, but the loop's decision was already based on the pre-await `c` values and may push the now-superseded local value or skip the new one because the dirty flag handling is interleaved across loops.
- Why it matters: On a large library with a slow network, a single 'Sync now' can run for seconds. A writer who reorders folders or flips a status during that window can see their change bounce back or not stick, because the reconcile is arbitrating against a snapshot taken before they acted. It is not silent content loss, but it makes sync feel unreliable : the opposite of the product's promise.
- Fix plan: Snapshot the local decisions up front (before any await) into a plan, or re-fetch listScripts and re-read all local meta at the start of each loop; simplest robust fix is to make reconcile idempotent and cheap to re-run, and to serialize it against user mutations with a single in-flight guard (a ref boolean) so a mutation during reconcile schedules a follow-up reconcile pass rather than racing it. Add a `reconcileInFlight` ref in useProjects; if a mutation lands while true, set a `reconcileAgain` flag and run once more when the current pass finishes.

### F7. Claim flow orphans version history (and can strand a script) on any id collision, with no user feedback

- Severity: qol | Verdict: unverified-qol | Confidence: medium
- Evidence: auth/claim moves versions only for scripts the destination does not already own, and moves scripts with the same NOT IN guard (functions/api/[[path]].ts:195-212). A source script whose id the destination already holds is deliberately NOT moved (content preserved) and its versions are left under srcId. After signInWithGoogle completes, the sync code is removed from localStorage (auth.ts:149), so the user can never authenticate as srcId again : any rows left behind become permanently unreachable. The client only checks `res !== null` (auth.ts:88) and never reads the (not-returned) moved count, so the user is told 'Imported' regardless of how much actually moved. The claim response for the code path returns `{ ok: true }` with no counts (path.ts:213).
- Why it matters: In the normal case UUID collisions never happen, so this is low-probability. But if it does (e.g. a script created before an id-remap, or a re-imported fdx that reused an id), the writer's version history for that script vanishes silently after they switch from a sync code to Google, and they are told the import succeeded. There is no path to recover it because the code is discarded.
- Fix plan: Have auth/claim return counts of moved scripts, moved versions, and skipped-due-to-collision ids. In signInWithGoogle/claimSyncCode, do not discard the sync code until the claim reports zero collisions (or keep a record of skipped ids). Surface a warning if anything was skipped. Server-side, consider moving orphaned versions of a colliding script under a renamed script_id rather than leaving them stranded, or explicitly deleting them so they do not accumulate under a dead user_id. Lowest-risk first step: return and log the counts so the silent case becomes observable.

### F8. Snapshot throttle can drop the only pre-edit backup during a burst, weakening the version-history safety net

- Severity: qol | Verdict: unverified-qol | Confidence: medium
- Evidence: pushNow gates snapshots behind a 3-minute throttle: `if (now - lastSnapshotAt.current > SNAPSHOT_THROTTLE_MS)` (useCloudSync.ts:146-152, SNAPSHOT_THROTTLE_MS = 3*60*1000 line 28). lastSnapshotAt is a per-mount ref initialized to 0 (line 90), so it resets to 0 on every editor remount (project switch, reload). restoreVersion/importContent take an explicit unthrottled snapshotLive first (line 318, 331), which is good, but ordinary editing relies entirely on the throttled periodic snapshot. A large rewrite done within 3 minutes of the last snapshot produces no new snapshot, and createSnapshot failures are swallowed (line 149-151 `.catch(console.error)`).
- Why it matters: The history panel is the writer's rollback safety net. If they make a sweeping deletion and a mistake within the 3-minute window and then keep editing, there may be no snapshot of the good pre-deletion state to roll back to : the periodic snapshot they were counting on never fired. This undercuts the 'never holds your scripts hostage / always recoverable' promise.
- Fix plan: Trigger an unthrottled snapshotLive before large structural changes (e.g. when a single update removes more than N nodes/characters, detectable in the onUpdate handler), independent of the 3-minute timer. Persist lastSnapshotAt across remounts (store in localStorage per project) so switching projects does not reset the cadence. Surface createSnapshot failures to the sync-status indicator instead of only console.error, so the user knows the safety net is not recording.

### F9. Folder reconcile pushes every reordered folder with client updatedAt but resolves conflicts by that same timestamp, so simultaneous edits on two devices can lose folder state via last-write-wins with no per-field clock

- Severity: qol | Verdict: unverified-qol | Confidence: medium
- Evidence: Folders have only a single updated_at clock (migrations 0001 folders table lines 23-33; there is no per-field clock like scripts got in 0004). reorderFolders bumps updatedAt for every moved folder (folders.ts:149-162), updateFolder bumps it for name/color/stage/parent changes (line 135), and reconcile pushes any locally-newer folder wholesale (useProjects.ts:410-418) and pulls any cloud-newer folder wholesale (line 421-427, upsertLocalFolder overwrites name/color/stage/parent/order). Because upsertCloudFolder sends the whole row (lib/cloud/folders.ts:37-49) and the PUT overwrites all columns (path.ts:238-242), a device that only reordered will overwrite a name/color change made on another device if its updatedAt is marginally newer.
- Why it matters: A writer renames a folder on their phone and reorders folders on their laptop around the same time. Whichever device syncs last wins the entire folder row, so either the rename or the reorder is silently lost. Folders are described as 'view organization, not the work itself', so this is lower stakes than script content, but it still makes cross-device folder state feel flaky.
- Fix plan: Either (a) split folder placement (position/parent) from folder metadata (name/color/stage) into separate clocks mirroring the scripts placed_at/title_at approach, adding a folders migration and a value-compare CASE in the PUT handler, or (b) make the folder PUT a partial update (only send the columns that actually changed on this device) so a reorder does not overwrite a name edit. Option (b) is the smaller change: have upsertCloudFolder accept a field mask and have reconcile push only the changed fields. Add a folder-level dirty/field-dirty flag like the scripts layer already has.
