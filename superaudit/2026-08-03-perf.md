# Audit: performance on real scripts and real libraries

A feature script is 100 to 120 pages. This app must stay responsive while
typing into one, with panels open, on a laptop. Nobody has measured it.

Scope: `lib/editor/**` only, plus new benchmark test files. Do NOT touch
`components/`, `lib/export/`, `lib/storage/`, `app/`, or `duet/`: parallel
audits own those.

## Method

Write benchmarks as tests using the existing headless kit. Generate synthetic
scripts of 10, 100, 500 and 2000 pages. Measure, then optimise what the
measurements actually show, and keep the benchmark as a regression guard with
a generous threshold so it fails only on a real regression.

## What to measure and fix

1. Per-keystroke cost on a 120-page script: every appendTransaction plugin
   (AutoCaps, AutoElement, contd, revisions, spell, breakdown) and every
   decoration pass. Anything that walks the whole document on every keystroke
   is the bug; make it walk only the changed range.
2. The outline and pagination recomputation: cost per keystroke, and whether
   they are debounced and incremental rather than total.
3. Autocomplete candidate building: it should not rescan the whole document to
   offer a character name.
4. Spell check over a long script with a large user dictionary.
5. Memory: no unbounded caches, no listeners accumulating per open, no
   retained references to old documents after switching projects.
6. The find plugin over a document with tens of thousands of matches.

Report the before and after numbers for each optimisation. Do not micro-
optimise anything the measurements show is already cheap: say so instead.

## Definition of done

`npx tsc --noEmit && npm test` pass, benchmarks included. Report at
`superaudit/2026-08-03-perf-report.md` with a table of measured timings before
and after, and anything slow that you chose not to change, with the reason.
